## 1. 产品目标

| # | 目标 | 要解决的痛点 | 可衡量标准 |
| --- | --- | --- | --- |
| G1 | **在线化插件交付** | 现在装/升级插件靠手动拷目录到 `public/plugins/`，手机端没法操作，门槛高、易出错 | 用户在手机 WebView 内完成安装/升级/卸载，全程不碰文件系统、不重装 APK；单个插件操作 ≤ 3 次点击 |
| G2 | **集中可信的分发来源** | 插件散落在群聊/网盘，无统一发现入口，版本新旧难辨，无来源可信度 | 提供统一插件来源（索引 + 包仓库），列表可见名称/版本/能力/来源；升级时能识别"有新版本" |
| G3 | **零风险兼容存量** | 担心升级插件会覆盖自定义插件、丢失密钥配置、破坏数据库 | 存量 6 个插件与 `plugin.json` 契约 100% 兼容；升级只动目标插件目录；`data/`（数据库、图片、密钥）零改动；密钥与启用状态保留 |

## 2. 用户故事

| # | 角色 | 故事 |
| --- | --- | --- |
| US1 | 手机端用户 | 作为手机端用户，我想在设置页看到"可安装的插件列表"，点一下就能装上，这样我不用连电脑拷目录 |
| US2 | 手机端用户 | 作为手机端用户，我想在插件有新版本时看到"可升级"提示并一键升级，且我填过的 API Key 不丢，这样我无感地用上最新引擎 |
| US3 | 手机端用户 | 作为手机端用户，我想一键卸载不再需要的插件，这样能关闭它的能力、保持插件列表干净 |
| US4 | 手机端用户 | 作为手机端用户，我想在安装前看到插件的详情（说明、能力、版本、作者、来源），这样我能判断它是否可信、是否是我要的 |
| US5 | 插件开发者 | 作为插件开发者，我想按规范把一个插件打成 zip 并推一个 tag 就发布到市场，这样我不用手工通知每个用户去拷文件 |
| US6 | 管理员/运维 | 作为管理员，我想配置插件来源地址，并在无网络时用"本地导入插件包"安装，这样在内网/离线场景也能用 |

## 3. 需求池

> 优先级：**P0 = 必须有（最小闭环）**；P1 = 应该有；P2 = 锦上添花。
> P0 闭环定义：**能从一个集中来源发现插件，并通过热更新完成"安装 → 升级 → 卸载"，且不破坏存量数据与配置。**

### P0 · 最小闭环

| 编号 | 需求 | 说明 / 验收要点 |
| --- | --- | --- |
| P0-1 | 插件市场入口 | 设置页新增"插件市场"入口，与现有"识别插件设置"并列并互相跳转 |
| P0-2 | 插件来源配置 | 可配置来源地址（索引文件 URL），支持默认值；保存后立即生效 |
| P0-3 | 拉取插件索引 | 从来源拉取插件索引（id/名称/版本/能力/说明/包地址），列表展示"已安装/可安装/可升级"状态 |
| P0-4 | 安装插件 | 下载插件包 → 校验 → 解压到 `public/plugins/<id>/` → 自动被发现；安装后可在设置页配置/启用 |
| P0-5 | 升级插件 | 检测到本地版本 < 来源版本时提供"升级"；**只覆盖该插件目录**，保留 `data/plugins.json` 中的密钥与启用状态 |
| P0-6 | 卸载插件 | 删除对应插件目录并清理其启用记录；需二次确认；**不得触碰 `data/` 下数据库/图片/密钥** |
| P0-7 | 插件包规范 | 定义包格式（zip）、根层级布局、`plugin.json` 必填与校验规则（复用现有契约，见 §6） |
| P0-8 | 安装安全校验 | id 与目录名一致、zip-slip 防护、文件大小/结构校验；校验失败即中止并给出可读中文错误 |
| P0-9 | 存量兼容 | 现有 6 个插件（mock-ocr、baidu-ocr、qwen35-ocr、mimo-v26-flash、ocr-ensemble、ocr-log）可直接被市场识别为"已安装"，无需重装、无需改清单 |
| P0-10 | 失败可回滚 | 安装/升级解压失败时保留原插件目录（临时目录 + 原子替换），避免出现"半安装"状态 |

### P1 · 应该有

| 编号 | 需求 | 说明 / 验收要点 |
| --- | --- | --- |
| P1-1 | 插件详情页 | 展示说明、版本历史、能力标签、作者、来源、包大小；作为安装前决策依据（US4） |
| P1-2 | 版本回退 | 保留上一版本，支持"回退到上一版本"（对齐服务端更新的可回退体验） |
| P1-3 | 自检集成 | 安装后引导跑 `check.php`（API 链接测试），复用现有自检契约 |
| P1-4 | 新版本提醒 | 进入市场时自动检测可升级数量，在入口显示角标 |
| P1-5 | 本地导入插件包 | 支持从手机文件选择器导入一个插件 zip（离线/内网场景，US6） |
| P1-6 | 插件发布流水线 | CI 按 tag 自动打包、校验、上传、更新索引（见 §6 工作流） |

### P2 · 锦上添花

| 编号 | 需求 | 说明 / 验收要点 |
| --- | --- | --- |
| P2-1 | 搜索 / 分类 / 能力筛选 | 按能力标签（`report.ocr`、`report.ocr.fusion`、`report.ocr.log`）筛选插件 |
| P2-2 | 多来源管理 | 支持同时配置多个来源并聚合展示 |
| P2-3 | 包签名校验 | 对插件包做签名（如 Ed25519），校验发布者身份（待 §7 拍板） |
| P2-4 | 评分 / 评论 / 下载量 | 社区反馈数据（需后端服务支持） |
| P2-5 | 付费 / 授权分发 | 收费插件与授权校验（待 §7 拍板） |
| P2-6 | 更新日志展示 | 在详情页展示每个版本的 changelog |

## 4. "插件分支"定位（产品侧建议）

| 项 | 建议 |
| --- | --- |
| 分支名 | `plugin`（插件开发/发布基线分支） |
| 定位 | 与主分支（服务端程序热更新，`web-v*` tag）**解耦**：`plugin` 分支专用于插件市场的开发、插件包规范落地与插件发布，主线继续负责系统功能 |
| 与 tag 的关系 | 插件发布用独立 tag 命名（建议 `plugin-<id>-vX.Y.Z`，如 `plugin-baidu-ocr-v1.2.0`），CI 按此规则触发插件打包，**与 `web-v*` 互不干扰** |
| 存量处理 | 从主分支 `public/plugins/` 下的 6 个存量插件作为"种子插件"迁入 `plugin` 分支，纳入市场首批内容；插件版本以各自 `plugin.json` 的 `version` 为准 |
| 回合并发策 | `plugin` 分支定期向主分支合并（规范、工具、种子插件更新）；主分支的系统升级仍遵循"不覆盖 plugins/ 下自定义插件"原则 |
| 交付物落地 | 《打包插件规范文档》《打包工作流文档》作为 `plugin` 分支的首批 docs 交付 |

## 6. 插件包与来源的初步设想（产品侧建议，技术细节交架构师）

### 6.1 插件包长什么样

| 项 | 建议 |
| --- | --- |
| 格式 | **zip**（与现有服务端热更新包一致，App/PHP 均可解压；沿用 zip-slip 防护经验） |
| 根层级 | zip 根目录**直接是插件内容**（`plugin.json`、`handler.php`、可选 `check.php`/`shared.php`），不额外套一层 id 目录，降低解析歧义；id 从清单读取并与目标目录名强校验 |
| 必含文件 | `plugin.json`（遵循现有契约）+ `entry` 指向的执行脚本 |
| 元数据 | 优先**复用 `plugin.json`**，不另造清单；如需市场展示字段（changelog、图标、包大小），可在索引文件中补充，避免插件包契约膨胀 |
| 大小上限 | 建议单包 ≤ 5MB（图片/大词典类资源走独立下载，初版不纳入） |
| 兼容性 | 存量 6 个插件按现有目录直接打包即可入库，无需改一行代码 |

### 6.2 插件来源 / 索引怎么组织

| 项 | 建议 |
| --- | --- |
| 分发通道 | **复用现有热更新通道**：包上传到与服务端热更相同的包仓库（现有 CI 用 Generic Package Registry + Release 挂链），App/PHP 按同一鉴权方式拉取，减少新基建 |
| 索引文件 | 一个集中索引（建议 `plugins-index.json`），逐条列出 `id / name / version / capabilities / description / author / package_url / changelog / min_system_version`；市场列表与版本比对都基于它 |
| 版本判定 | 以 `plugin.json` 的 `version`（语义化）为准，本地版本 < 索引版本即"可升级"；与系统版本号解耦 |
| 信任机制 | 初版靠"来源配置 + HTTPS + 仓库鉴权"背书；签名校验作为 P2 增强（待 §7 拍板） |
| 离线兜底 | 支持本地导入 zip（P1-5），覆盖内网/无网络场景 |

### 6.3 《打包插件规范文档》要点（后续交付物大纲）

1. 插件目录结构与命名（id 规则、必选/可选文件）
2. `plugin.json` 字段契约（**完全沿用现有文档 §3，不新增必填项**）
3. zip 打包布局、大小上限、zip-slip 与路径规范
4. 版本规则（语义化版本、与系统版本独立）
5. 校验清单（id=目录名、entry 存在、JSON 合法、能力标签合法）
6. 存量插件入库示例

### 6.4 《打包工作流文档》要点（后续交付物大纲）

1. 开发者本地开发 → 自检（`check.php`）→ 提交到 `plugin` 分支
2. 打 `plugin-<id>-vX.Y.Z` tag 推送
3. CI 触发：校验清单 → 打包 zip → 上传包仓库 → 更新 `plugins-index.json` → 生成 Release/变更记录
4. 手机端"插件市场"刷新即可发现新版本 → 一键升级
5. 失败处理：校验失败阻断发布、版本冲突处理、回滚流程
6. 权限与鉴权：谁可打 tag / 发布，包仓库访问凭据管理

## 7. 待确认问题（需用户拍板）

| # | 问题 | 选项 / 影响 |
| --- | --- | --- |
| Q1 | 插件来源用哪个仓库？ | ①与 baogong-system 同仓库（复用现成 CI/鉴权，最快）；②独立插件仓库（隔离更清晰，需新基建）。**建议①** |
| Q2 | 来源平台到底用 GitHub 还是 GitLab？ | 背景描述为 GitHub Releases，但现有 CI（`.gitlab-ci.yml`）实为 GitLab Generic Package Registry。二者鉴权/直链行为不同，需统一后再定索引与下载实现 |
| Q3 | 是否需要包签名 / 发布者身份校验？ | 涉及开发成本与钥匙管理。建议初版不上（P2），但需确认安全底线 |
| Q4 | 是否收费、是否做付费/授权分发？ | 影响是否有支付、授权校验、用户体系。初版建议全部免费、不做授权（P2） |
| Q5 | 存量 6 个插件如何处理？ | 是否全部迁入市场作为种子？版本基线如何取值？是否允许在市场内升级官方内置插件？ |
| Q6 | 通过什么执行下载/解压？ | PHP 后端直接下载写入 `plugins/`（无需改 APK，推荐）还是必须 App 原生介入？需架构师确认 PHP 出网与写权限（现有 `lib/net.php` 已封装出网） |
| Q7 | 升级时的配置保留策略边界 | 明确"保留密钥/启用状态/用户设置"，但新增配置项的默认值如何合并？是否覆盖插件自带文件？ |
| Q8 | 插件分支与主分支的合并节奏 | `plugin` 分支多久向主分支合并一次？系统热更新包是否包含 `plugins/` 存量插件（当前包含，需注意与市场上插件版本冲突） |

## 8. 兼容性与边界（硬性约束，不可妥协）

| 约束 | 说明 |
| --- | --- |
| 存量插件 | 6 个插件、`plugin.json` 契约、能力标签体系 100% 兼容，零迁移成本 |
| data/ 不覆盖 | 任何安装/升级/卸载操作**绝不触碰** `data/`（数据库、图片、`plugins.json` 密钥、日志、快照） |
| 系统升级独立 | 服务端程序升级（`web-v*`）仍不覆盖 `plugins/` 下自定义插件；插件版本与系统版本互不绑定 |
| 启用状态与密钥 | 存于 `data/plugins.json`，升级插件时原样保留，密码字段继续掩码回显 |
| 不重装 APK | 插件的安装/升级/卸载全部在运行态完成，用户无需重新打包或安装 APK |
